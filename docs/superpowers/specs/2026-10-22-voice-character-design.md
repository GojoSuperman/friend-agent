## 1. 왜 만드나

14강 과제 발표 때 시연할 기능이다. 지금 friend-agent는 글자로 주고받는 채팅이라 화면이 밋밋하다. 마이크로 말을 걸면 캐릭터가 **목소리로 답하고, 화면의 2D 캐릭터가 듣기·생각·말하기에 맞춰 움직이게** 해서 시연을 재미있게 만든다.

동시에 이 변경을 **작업 브랜치 → PR → 머지 → GitHub Actions 자동 배포** 흐름으로 내보내서, 사람이 배포 명령을 치지 않아도 사용자 화면에 새 기능이 나오는 것을 보여 주는 것이 과제의 본래 목적이다.

## 2. 목표 / 비목표 / 반목표

**목표**
- 마이크 버튼으로 말하면 글자로 바뀌어 기존 대화 API(`/api/chat`)로 간다.
- 캐릭터의 답을 목소리로 읽어 준다.
- 2D 일러스트 캐릭터가 상태에 따라 움직인다: 대기 · 듣는 중 · 생각 중 · 말하는 중.
- 처음 들어오면 **캐릭터 2명(여성 "하루", 남성 "준호")** 중 하나를 고른다. 두 캐릭터는 목소리 높낮이가 귀로 구분된다.
- 무료로 한다. 외부 유료 API를 쓰지 않는다.

**비목표 (이번에 안 함, 나중에 고도화)**
- 나이대별(20~50대, 노년) 캐릭터, 캐릭터 3명 이상
- 타입캐스트 등 외부 음성 서비스, 엣지 브라우저 전용 남성 목소리
- 입 모양을 실제 발음에 맞추는 립싱크 (말하는 동안 입이 뻐끔거리는 정도면 된다)
- 서버(백엔드) 기능 변경 — 이 PR에서는 하지 않는다. 서버 변경은 PR ①(11절)에 모은다

**반목표 (돌아가도 이러면 실패)**
- 글자 채팅이 깨진다. 마이크가 안 되는 상황에서도 글자 입력으로 시연을 이어갈 수 있어야 한다.
- `app/persona.py` 고정 규칙, `app/safety.py` 안전장치가 약해진다.
- 비밀값이 화면 코드에 들어간다, 유료 호출이 생긴다.
- 기존 테스트(`pytest`)가 깨진다.

## 3. 제약

- **브라우저 내장 음성만 쓴다** (Web Speech API).
  - 듣기: `SpeechRecognition`(크롬은 `webkitSpeechRecognition`), `lang = "ko-KR"`.
  - 말하기: `speechSynthesis` + `SpeechSynthesisUtterance`.

- 저장소 작업 규칙(`AGENTS.md`)을 따른다. 특히 액션 버전 변경 금지, 비밀값 금지, 안전 규칙 약화 금지.

## 5. 동작 설계

### 5.1 화면

- **캐릭터 고르기 화면**: **접속할 때마다** 대화 화면 앞에 하루/준호 카드 2장이 보인다. 이미 캐릭터가 있으면 그 캐릭터 카드가 선택된 상태로 보인다. 카드마다 "▶ 목소리 듣기" 미리듣기가 있고, 카드를 누르면 그 캐릭터로 대화를 시작한다. *(내 판단: 이 클릭이 브라우저 자동 재생 제한을 푸는 계기가 되어, 이미 캐릭터가 있는 시연 계정도 첫 인사를 소리로 듣게 하기 위함)*
  - 캐릭터가 없는 첫 사용자도 기존 "캐릭터 만들기" 설정 폼 대신 이 고르기 화면을 먼저 본다. 고른 뒤 세부 설정은 왼쪽 메뉴의 "캐릭터 설정"에서 한다. *(내 판단)*
  - 고르면 현재 캐릭터 설정 전체를 읽어 `name`, `gender`만 바꿔 `/api/character`로 저장한다(하루=여성, 준호=남성). 이미 다른 이름을 지어 두었어도 카드의 이름으로 바뀐다. 성격·말투 등 나머지는 그대로 둔다. 설정에서 빠진 필드는 서버가 기본값으로 채우므로 반드시 전체를 보내야 한다. *(내 판단)*
  - 왼쪽 메뉴의 "캐릭터 설정" 화면은 그대로 둔다. 거기서 성별을 바꾸면 일러스트와 목소리도 그 성별을 따른다. "밝히지 않음"은 여성 일러스트·목소리로 보여 준다. *(내 판단)*
- **대화 화면 = 무대형(A)이 기본, 대화 기록을 펼치면 나란히형(B)**. *(내 해석: "A와 B 둘 다"를 한 화면의 두 상태로 구현)*
  - A: 가운데에 캐릭터를 크게, 아래에 답 자막, 그 아래 🎤 버튼. 맨 아래에 글자 입력창(비상용).
  - "💬 대화 기록" 버튼을 누르면 오른쪽에 기존 대화 말풍선 목록이 열리고 캐릭터는 왼쪽으로 줄어든다(B). 다시 누르면 닫힌다. 열림 상태는 브라우저에 기억한다.
  - 좁은 화면(휴대폰)에서는 대화 기록이 아래로 쌓인다.
  - 왼쪽 메뉴(대화 · 캐릭터 설정 · 기억과 약속)와 개발용 "이번 턴" 패널은 지금처럼 둔다.
- 기존 동물 이모지 아바타(🐻 등)는 대화 화면의 캐릭터 자리에서는 일러스트로 대체한다. 메뉴의 작은 아바타 표시는 만드는 사람 판단.

### 5.2 캐릭터 상태와 움직임

| 상태 | 언제 | 움직임 |
|---|---|---|
| 대기 | 아무 일 없을 때 | 숨쉬기(살짝 커졌다 작아짐), 가끔 눈 깜빡임 |
| 듣는 중 | 🎤를 눌러 음성 인식 중 | 고개 갸웃, 마이크 버튼 강조 |
| 생각 중 | 메시지를 보낸 뒤 첫 음성이 나오기 전 | 점 세 개 깜빡임 |
| 말하는 중 | 목소리가 나오는 동안 | 입 뻐끔, 몸 살짝 흔들림 |

말하는 중 상태는 음성의 시작·끝 이벤트(`onstart`/`onend`)로 켜고 끈다.

### 5.3 듣기 (음성 → 글자)

- 🎤를 한 번 누르면 듣기 시작, 말이 끝나 조용해지면 자동으로 멈춘다. 다시 누르면 바로 멈춘다.
- 듣는 동안 중간 인식 글자를 자막 자리에 흐리게 보여 주고, 확정된 문장을 기존 `send(text)`로 보낸다.
- 캐릭터가 말하는 중에 🎤를 누르면 말하기를 멈추고 듣기 시작한다(끼어들기).
- 마이크 권한 거부·인식 실패·지원하지 않는 브라우저면 짧은 안내를 띄우고 글자 입력으로 쓸 수 있게 둔다.

### 5.4 말하기 (글자 → 음성)

- 캐릭터의 답(`delta` 이벤트로 오는 글)을 **문장 단위로 끊어** 순서대로 읽는다. 첫 문장이 완성되면 바로 읽기 시작해서 기다리는 시간을 줄인다. 긴 글을 한 번에 넘기면 크롬 온라인 목소리가 중간에 끊기는 문제도 피한다.
- 마이크로 보낸 말뿐 아니라 **글자 입력·추천 문장으로 보낸 말의 답도 읽는다.** 소리를 원하지 않으면 🔇로 끈다. *(내 판단)*
- 이모지와 URL은 읽지 않는다.
- 목소리 설정 *(실측값을 참고한 내 판단, 화면에서 들어 보고 조정)*:

  | 캐릭터 | 목소리 | 높낮이(pitch) | 빠르기(rate) |
  |---|---|---|---|
  | 하루(여성) | Google 한국의 | 1.1 | 1.05 |
  | 준호(남성) | Google 한국의 | 0.6 | 0.95 |

  - 근거: 목소리 테스트에서 사용자가 남성 캐릭터들을 `Google 한국의` 0.6~0.95로 조절해 들었다(남성-30대 0.6 / 1.0). 다만 최종 확정값은 아니므로, **구현 첫 단계에서 시연 PC 크롬으로 두 캐릭터를 들어 보고 귀로 구분되는지 확인**한다. 구분이 안 되면 준호에 `Microsoft Heami`를 쓰는 등 목소리 자체를 다르게 한다.
  - `Google 한국의`가 없으면 다른 한국어 목소리, 한국어 목소리가 하나도 없으면 음성 없이 자막만 보여 준다.
  - 엣지처럼 남성 한국어 목소리가 있는 브라우저면 준호에 그 목소리를 쓰고 높낮이는 1.0 근처로 둔다.
- 앱을 열 때 먼저 말 걸기(`greet`)와 약속 알림 메시지도 같은 방식으로 읽는다. 단, 브라우저 자동 재생 제한 때문에 **사용자가 한 번 클릭한 뒤부터** 소리를 낸다(캐릭터 고르기 클릭이 그 계기).
- 🔇 음소거 버튼을 둔다(발표 중 소리를 꺼야 할 때).

## 7. 배포 흐름 (과제 1)

1. 전제: 14강 섹션 3~5(hello 워크플로, WIF 권한, `deploy.yml`)가 끝나 main 머지 시 자동 배포가 도는 상태.

## 8. 성공 기준 (실행 전에 적어 둠)

시연 PC 크롬에서 Cloud Run 서비스 URL로 열었을 때:

1. 캐릭터 고르기 화면에서 하루·준호의 미리듣기 목소리가 **귀로 구분된다**.
2. 🎤를 누르고 "내일 날씨 어때?"라고 말하면 인식된 글자가 보이고, 캐릭터가 생각 중 → 말하는 중으로 바뀌며 답을 목소리로 읽는다. 말하는 동안 입이 움직이고 끝나면 멈춘다.
3. "내일 아침 8시에 물 마시라고 알려 줘"를 말하면 약속이 저장되고(기존 기능), 답을 목소리로 읽는다.
4. 대화 기록 버튼으로 A ↔ B 배치가 바뀐다.
5. 마이크 권한을 거부해도 글자 입력으로 대화가 된다.
6. `pytest`가 모두 통과한다.
7. 위 결과가 PR 머지 → 자동 배포로 나간 리비전에서 확인된다(`/version` commit 일치).

## 11. PR ①: 접속 잠금 + 방문자 LLM 키 등록

### 왜

시연 URL은 공개 주소라 누구나 들어와 내 LLM 키로 비용을 쓸 수 있다. 커밋되지 않은 채 있던 **접속 코드 잠금**(`app/access.py`, `tests/test_access.py`, `app/config.py`, `app/main.py`)에 더해, **방문자가 자기 LLM API 키를 등록하면 그 키로 쓸 수 있게** 한다(사용자 결정).

### 동작

- `ACCESS_CODE`가 설정된 배포에서 잠금 화면(`/access`)에 길이 두 개가 있다. *(두 길을 함께 두는 것은 내 판단: 발표자는 지금처럼 서버 키로, 방문자는 자기 키로)*
  1. **접속 코드 입력** → 지금 만든 그대로. 서버 키(`llm-api-key`)로 대화.
  2. **내 API 키로 쓰기** → 제공자(OpenAI · Gemini · Claude 중 하나, `app/config.py`의 `PROVIDERS`)를 고르고 키를 넣는다. 이후 그 브라우저의 요청은 그 키로 LLM을 부른다. 모델은 제공자의 기본 모델(`PROVIDERS[...]["model"]`).
- `ACCESS_CODE`가 없으면(로컬 실행) 지금처럼 잠금 없이 서버 키로 동작한다.
- 대화 화면에 지금 어느 키로 쓰는 중인지(서버 키 / 내 키) 작게 표시하고, "내 키 지우기"를 둔다.

### 키 다루는 규칙 (반드시)

- 키는 **브라우저의 sessionStorage에만** 둔다(탭을 닫으면 사라짐). 서버·DB·쿠키에 저장하지 않는다. *(sessionStorage는 내 판단: 시연용이라 기억할 필요보다 남지 않는 쪽이 낫다)*
- 요청마다 HTTPS 헤더로 보낸다(예: `X-LLM-Provider`, `X-LLM-Key`). 서버는 그 요청에서만 LLM 객체를 만들어 쓰고 버린다(`get_llm` 의존성에서 분기).
- 키를 **로그·오류 메시지·화면·`/api/config` 응답 어디에도 남기지 않는다.** 로그에는 "방문자 키 사용 여부"와 제공자 이름만 남긴다.
- 키 없이·잠금 미통과로 `/api/*`를 부르면 지금처럼 401.
- 키가 틀리면(제공자 인증 오류) "키를 확인해 주세요"라고만 알리고, 원문 오류는 화면에 보내지 않는다.
- `/health`는 계속 열어 둔다. `/version`은 잠금 대상으로 둔다(14강 확인 때는 접속 코드 입력 후 연다). *(내 판단)*

### 방문자 데이터 분리 (반대 검토 반영)

- 키는 형식만 검사할 수 있어서, 가짜 키로도 LLM 외 API(대화 기록, 데이터 삭제 등)가 열린다. 그래서 **방문자는 탭마다 만든 무작위 방문자 ID로 `visitor:<ID>` 사용자가 되어 자기 데이터만** 본다. 발표자(접속 코드, `local-user`) 데이터는 보이지도 지워지지도 않는다.
- 방문자는 사진 글자 읽기(`/api/ocr`)를 쓸 수 없다(서버 CPU 비용).
- 방문자 헤더는 **잠금(`ACCESS_CODE`)이 켜져 있을 때만** 읽는다. 로컬은 지금과 완전히 같다.
- 틀린 키뿐 아니라 잔액·한도가 없는 키(429 quota), Gemini의 400 "API key not valid"도 같은 안내로 보여 준다. 서버 키의 오류는 방문자 안내로 바꾸지 않는다.

### 받아들인 한계 (이번에 고치지 않음)

- 요청 수 제한이 없다. 이 서버로 남의 키가 유효한지 확인해 볼 수 있다(시연 기간 한정 공개라 받아들임).
- 방문자 데이터는 서버 메모리에 쌓이고 재배포 때 사라진다.

### 성공 기준

1. 접속 코드로 들어가면 서버 키로 대화된다(기존 동작 유지).
2. 다른 브라우저(시크릿 창)에서 내 OpenAI(또는 Gemini) 키를 넣으면 대화되고, 그 대화의 LLM 호출이 그 키로 나간다(제공자 사용량 화면에서 확인).
3. 키 없이 `/api/chat`을 부르면 401.
4. Cloud Run 로그에 키 문자열이 한 번도 나오지 않는다(로그 검색으로 확인).
5. 틀린 키를 넣으면 친절한 안내가 나오고 서버가 죽지 않는다.
6. 접속 잠금·키 등록 테스트를 `tests/`에 추가하고 `pytest` 전체 통과.
